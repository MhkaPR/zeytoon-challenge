# API Contract: Versioned Backend Conventions

**Feature**: `004-backend-contract`
**Date**: 2026-11-05

This contract defines the HTTP interface every backend application must follow. It
applies to the existing `accounts`, `companies`, `catalog`, and `admin_console` APIs and
to every future API.

## 1. Versioning and Routing

- All application routes are mounted under `/api/<version>/`.
- The current version is `v1`.
- Version routing is declared in `config/api/v1/urls.py`.
- A new version is introduced only for a major breaking change.
- The health check lives outside the versioned routes at `/api/health/`.

## 2. Viewset Rules

- Use `ModelViewSet` for standard CRUD over a model.
- Use `GenericViewSet` with the needed mixins for partial CRUD.
- Use `@action` for non-CRUD endpoints on a viewset.
- A bare `ViewSet` is allowed only when no generic viewset or mixin applies.
- `APIView` is not allowed.
- Do not override `as_view` to reimplement routing.
- Mount viewsets with a DRF router.

## 3. Request Validation

- Every request body is validated by a DRF serializer.
- Invalid input returns a structured error before business logic runs.
- Pydantic is not imported in API or serializer modules.
- Query parameters for filtering, search, and ordering are handled by django-filter,
  `SearchFilter`, and `OrderingFilter`.

## 4. Response Shape

### Collection

```json
{
  "data": [
    {"id": 1, "name": "example"}
  ],
  "page": {
    "count": 1,
    "next": null,
    "previous": null
  }
}
```

### Detail or mutation

```json
{
  "data": {
    "id": 1,
    "name": "example"
  }
}
```

### Rules

- Every response body is produced by a serializer.
- Field names are snake_case.
- A model instance uses a `ModelSerializer`.
- A computed or aggregate payload uses `Serializer` or `BaseSerializer`.
- Views do not assemble response dictionaries inline.

## 5. Errors

Validation and domain errors use the shared error contract:

```json
{
  "error": {
    "code": "invalid_field",
    "message": "Some fields are missing or invalid.",
    "fields": {
      "email": "This field is required."
    }
  }
}
```

Rules:

- `code` is a stable snake_case identifier.
- `message` is human-readable and safe to show.
- `fields` is present for field-level validation errors.
- HTTP status codes are meaningful: 400 validation, 401 unauthenticated, 403
  forbidden, 404 not found, 409 conflict, 429 throttled, 5xx server or upstream
  failure.

## 6. Authentication

- Phone-only OTP authentication is the default flow.
- Successful authentication issues a JWT access token and a rotating refresh token.
- Email and username login are not supported.
- Public endpoints explicitly allow anonymous access.
- Every other endpoint requires authentication.
- Operator endpoints require an operator permission backed by Django groups or
  django-guardian, not an ad-hoc boolean flag.

## 7. Pagination, Filtering, and Throttling

- Pagination uses the default page-size pagination class.
- Filtering, search, and ordering use the standard DRF filter backends.
- CORS uses the standard CORS library with an explicit allowlist.
- Throttling uses the standard DRF throttling classes.
- CSRF is disabled for token-based API endpoints.

## 8. Documentation

- The OpenAPI schema is generated by drf-spectacular.
- The schema is served at `/api/schema/`.
- The interactive documentation is served at `/api/docs/`.
- Every request and response serializer is reflected in the schema.

## 9. Verification Checklist

- [ ] Every route is under `/api/v1/`.
- [ ] Every endpoint is a viewset action.
- [ ] Every response body is serializer-produced.
- [ ] Every request body is serializer-validated.
- [ ] No Pydantic import exists in an API or serializer module.
- [ ] Every collection uses `data` plus optional `page`.
- [ ] Every detail or mutation uses `data`.
- [ ] All field names are snake_case.
- [ ] The schema lists every endpoint.
- [ ] Public and operator permissions are explicit.
