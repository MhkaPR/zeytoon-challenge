# Phase 1 Data Model: Backend Development Contract Compliance

**Feature**: `004-backend-contract`
**Date**: 2026-11-05

This feature is a development contract, so its "entities" are the structural and
behavioral objects that the backend must expose. The domain models are listed as an
inventory that must comply with the contract.

## Contract Entities

### Application Module

Represents one backend application.

| Field | Type | Rules |
|---|---|---|
| `name` | string | Unique application label; matches the `apps.<name>` package. |
| `models_package` | directory | Contains one module per model or cohesive model group. |
| `views_package` | directory | Contains `v1/` (and later versions) with DRF viewsets. |
| `serializers_package` | directory | Contains `v1/` (and later versions) with DRF serializers. |
| `services_package` | directory | Contains `v1/` (and later versions) with class-based services. |
| `tests_package` | directory | Contains the application's tests; version-specific tests live in `tests/v1/`. |
| `tasks_module` | module | Optional; defines framework tasks for the application. |

**Relationships**: An application owns its models, views, serializers, services, and
tests. It may depend on another application only through the other application's
declared interface.

**Validation rules**:

- The models package initializer re-exports classes and defines no model.
- Version directories exist only under views, serializers, and services.
- No loose view, serializer, or service module remains at the application root.

### Versioned API Route

Represents a route group mounted under a version segment.

| Field | Type | Rules |
|---|---|---|
| `version` | string | Starts at `v1`; increments only for a major breaking change. |
| `base_path` | string | `/api/<version>/`. |
| `resource` | string | snake_case resource segment. |
| `viewset` | class | A generic DRF viewset or model viewset. |
| `actions` | list | Standard CRUD plus `@action` methods for extras. |

**Relationships**: A route belongs to one application and resolves to one viewset.

**Validation rules**:

- No `APIView`.
- No custom `as_view` routing override.
- Every response body is serializer-produced.

### Serializer Contract

Represents the request and response shape of an endpoint.

| Field | Type | Rules |
|---|---|---|
| `kind` | enum | `model` or `computed`. |
| `direction` | enum | `input`, `output`, or both. |
| `fields` | mapping | snake_case names; documented in the generated schema. |
| `validation` | rules | Declared on the serializer, not in the view or a Pydantic model. |

**Relationships**: A serializer belongs to one application and one API version.

**Validation rules**:

- Input serializers are DRF `Serializer` or `ModelSerializer`.
- Output serializers are DRF `Serializer`, `ModelSerializer`, or `BaseSerializer`.
- No Pydantic import in an API or serializer module.

### Response Envelope

Represents the outer shape of every API response.

| Field | Type | Rules |
|---|---|---|
| `data` | object or list | Required. |
| `page` | object | Optional; present on paginated collections. |

**Validation rules**:

- Collection: `{"data": [...], "page": {...}}`.
- Detail or mutation: `{"data": {...}}`.
- Field names are snake_case.

### Soft-Delete Base and Manager

Represents the shared deletion behavior.

| Field | Type | Rules |
|---|---|---|
| `deleted_at` | datetime or null | Set by soft delete; null means active. |
| `created_at` | datetime | Set on creation. |
| `updated_at` | datetime | Updated on save. |
| `objects` | manager | Excludes records with `deleted_at` set. |
| `deleted_objects` | manager | Includes only records with `deleted_at` set. |
| `delete()` | method | Soft delete. |
| `hard_delete()` | method | Physical delete. |

**Relationships**: Every domain model inherits this base.

**Validation rules**:

- One shared implementation in `apps/utils/models/`.
- No third-party soft-delete library.
- No per-model inline deletion flag.

### Audit Entry

Represents the recorded history of a model change.

| Field | Type | Rules |
|---|---|---|
| `actor` | user or null | Captured by middleware when available. |
| `action` | enum | Create, update, or delete. |
| `target` | model instance | The changed record. |
| `timestamp` | datetime | Recorded by the audit library. |
| `changes` | mapping | Field-level before/after values. |

**Relationships**: An audit entry references one model instance and optionally one user.

**Validation rules**:

- Every domain model is registered with django-auditlog.
- The audit middleware is enabled.

### Migration

Represents an ordered, immutable schema change.

| Field | Type | Rules |
|---|---|---|
| `app_label` | string | Owning application. |
| `number` | string | Next sequential number. |
| `operations` | list | Generated by the framework. |
| `dependencies` | list | Previous migrations and cross-app dependencies. |

**Validation rules**:

- A new file is created for every model change.
- Existing files are never edited.
- `makemigrations --check --dry-run` reports no pending changes.

### Service Version

Represents a class-based business contract.

| Field | Type | Rules |
|---|---|---|
| `version` | string | `v1`, `v2`, and so on. |
| `class` | class | Owns the business behavior. |
| `public_methods` | list | The contract exposed to callers. |

**Validation rules**:

- Business logic lives in a class, not a loose function or a view.
- An incompatible change adds a new version; the old version remains.

### Task

Represents a unit of background work.

| Field | Type | Rules |
|---|---|---|
| `name` | string | Unique task function name. |
| `decorator` | `@task` | Provided by the framework. |
| `backend` | setting | Selected through the `TASKS` setting. |
| `enqueue()` | method | The only dispatch path. |

**Validation rules**:

- Tasks live in the owning application's `tasks.py`.
- Application code does not assume a specific backend.
- Tasks are enqueued, not called directly.

### Admin Console

The admin console has no domain models of its own. It exposes the operator approval
queue and console endpoints and reads or mutates pipeline state through the pipeline
application's declared interface. The approval queue reads company data through the
companies interface.

### Removed

The `notifications` application and its models (`Notification`,
`NotificationDelivery`, `NotificationRecipient`) are removed from the project. No
remaining model, service, URL, setting, or test may reference them.

## State Transitions

### Link pipeline stage

`discovered` → `captured` → `extracted` → `plans_extracted` → `published`, with
terminal or parked states `no_price_tables`, `awaiting_llm_budget`, `flagged`, and
`dead_lettered`. A rerun resets a parked link to the last resumable stage.

### Replay run

`scheduled` → `running` → `succeeded` or `failed`, with `awaiting_llm_budget` as a
parked state.

### Capture session

`pending` → `recording` → `stored` or `failed`. A link may have at most one
non-terminal capture session.

### Company verification

`pending` → `verified` or `not_verified` through an append-only operator decision.
Approval starts the site lifecycle; rejection reopens registration.

## Validation Rules from Requirements

- Every API response is serializer-produced and uses the `data` envelope.
- Every API input is validated by a DRF serializer.
- Every model is soft-deleted and audited.
- Every schema change is a new migration.
- Every service contract is class-based and versioned.
- Every task is framework-defined and enqueued.
- Every runtime tunable is configurable.
